# reader_gw - the reader's gateware

FPGA code for the JLR MOST reader (Sipeed Tang Nano 20K, GW2AR-LV18). One clock, the
receiver's 99 MHz; nothing follows the ring but a tick train. What is new against
MOST25-to-AUDIO is the control-channel decoder that replaces the ESP32 host and the frame
train that replaces the Si514 ring clock; the receiver, the DSP engine and the S/PDIF coding
come over from `MOST25-to-AUDIO/listener_gw`.

## ctrl_decode

Input: the frame bytes as `rx_framer` writes them (`byte_we`, `byte_addr`, `byte_data`,
`frame_done` with `frame_par`, the block index and `blk_known`, `locked`). Bytes 61 and 62 of
the 16 frames of a block make the 32-byte control message; the block is taken when its last
frame completes with the index known and the receiver locked, exactly as `ctrl_uart.v` took it.

Integrity (audit R02). The block's CRC cannot be checked, its polynomial is not known; a
line-code error already costs the block (`rx_framer` drops `blk_known`). What biphase mark
lets through unseen is a lost mid-cell transition, a 1 read as 0, and the frame parity catches
that: its sense is not documented, but it is one value on every clean frame of a ring, so the
decoder learns it - 64 locked frames of one parity in a row - and from then on a block with a
frame of the other parity is dropped. Four such frames in a row mean the premise was wrong (a
parity that is not over the whole frame): the sense is forgotten and learnt anew, so a ring
whose parity varies is never filtered. The CRC comes once a capture gives it.

A block is a telegram under the rules the host's `most_msg.c` used - `virtual_most_source/control.py`
holds them and is cross-checked against that C code (`tools/crosscheck_most_msg.py`): message
type 0, a data byte other than 00/FF, TelID 0 (every message here fits one telegram), target
0x0010..0x0FFF, source logical or static, TelLen at most 12 (11 to a group). The *Ack OPTypes
carry a 2-byte SenderHandle, skipped.

The messages, by FBlock, FktID and OPType. The InstID is never checked (audit R07: a request may
name instance 0 or 0xFF, the answer the real one); the addresses only pair a request with its
answer - a request's device is its target, an answer's its source.

| Message | Taken as |
|---|---|
| 0x22 0x111 Connect, StartResult(Ack) `[SinkNr, SrcDelay, ch...]` | sink 1..4 is stream 0..3; the position takes effect at once, unconfirmed until the device's Result `[SinkNr]`; its Error turns every unconfirmed Connect to that device off (R08); a Result with nothing on, or from another device, changes nothing |
| 0x22 0x110 SinkInfo, Status `[SinkNr, DataType, Resolution, AudioChannels, SinkDelay, ch...]` | the device's own word on its sink, confirmed as it comes; any other SinkInfo on the sink means nothing is known: off |
| 0x22 0x112 DisConnect, StartResult(Ack) `[SinkNr]` | the stream off, if to the device the position came from |
| 0x22 0x113 Mute, Set/SetGet/Status `[SinkNr, Status]` | sink 0 = all, kept for every stream whether connected yet or not (R04); bit 0 = mute |
| 0x22 0x46D SpeakerLevel, Set/SetGet/Status `[param, SinkNr, dB...]` | the loudest speaker, signed dB |
| 0xF0 0x409, Status | byte 2 the audio level, byte 8 navigation and phone, byte 10 the parking sensors, raw |

The sinks are JLR's as mObridge's MOST25 DA guide (pp. 18-19) lists them for Jaguar and Land
Rover: 1 the main source, 2 phone, navigation and voice, 3 the parking sensors, 4 the chimes.

Formats (audit R09): from a SinkInfo the full tuple - PCM only, 2 or 3 bytes a sample, 1 or 2
channels, the list exactly Resolution x AudioChannels long. A Connect carries the list alone;
4 channels are taken as 16-bit stereo and 2 as 16-bit mono, the formats JLR is on record with
(STX 5.4.1.1: L-Hi, L-Lo, R-Hi, R-Lo), and a list of 3 or 6, which could be 24-bit stereo or
three 16-bit channels, is refused until a SinkInfo names the format. Channels are 0..59,
ascending; frame byte = channel + 1.

A stream's gain, as the host chose it, with streams 2 and 3 added: muted, 0; its own SpeakerLevel
in dB; else the 0x409 level of its kind - stream 2 (the parking sensors) byte 10, then byte 8,
stream 1 byte 8; else the volume - SpeakerLevel to sink 1, else 0x409 byte 2 - but never for
stream 3, the chimes (no volume message is on record for them, and a chime must not vanish with
the volume turned down); else the stream's start-up level. The start-up levels: the main source
at -12 dB (a quarter of full amplitude), the others at figures of their own (-6 dB until set
otherwise, and for good for the chimes unless a SpeakerLevel names sink 4), all four in
`sim/gain_tables.py`, and the first coefficient set after reset carries them, so a Connect is
heard before any level message.
`run_ctrl.py` asks these rules of the model directly before it holds the RTL to the model.
Positions survive a lost lock (R06: a gap must not silence the one output); a ring restart takes
the FPGA's supply with it and so clears everything.

Output: the command bus `host_cmd.v` gave `amp_out` in MOST25-to-AUDIO (`ok`, `cmd`, `p`). A
change of a stream's position sends command 01 for it. A level or mute message rewrites the
whole coefficient set as the host did: 49 words, eight straight biquads, k x gain per stream
and output (k = 1/256: a step settles in 5 ms), 1 - k, the commit with the last word, all
carrying the set's tag (amp_out switches banks only on a whole set of one tag, R03). One
command a clock, about 60 clocks a set; the next block cannot complete for another 16 frames.

## nco_frame

The ring's frame rate as a tick train on the receiver's clock: 1024 ticks a frame, the time
base `amp_out`'s engine starts on and `spdif_tx` draws its half-cells from (`phase_n`, as
`tdm_out` gave it before). Each tick is placed to one sample of the receiver's 792 Msps grid,
so an edge drawn from it through OSER8 sits on that grid, not on the 10.1 ns clock grid.

The period is the mean over the last 2^m frames of the receiver's frame starts (`fe_t` of UI 0,
the same time base), m growing with the frames seen since the lock up to 64: from the second
frame on it is the ring's to one sample in two frames (60 ppm), from the 64th to 20 ps a tick.
The nominal 48 kHz period counts for the first frame only. The frame's UI 0 falls at phase
896, so the train's frame start (phase 0) comes 128 ticks after it, 2.6 us after the frame
before has completed, when its bytes are long collected. On the first frame edge after a lock
the train is pinned there; after that each edge's error against the tick of that phase is taken
out by 1/16 with its fraction (taken to whole samples it would leave a dead zone the offset could
sit anywhere in). An error over 128 samples means the train is not tracking (the ring jumped): it
is pinned anew, and the period's history starts anew with it, so the jump never sits inside a
span. The train runs from a frame start once two edges in a row were within 4 samples with
the period measured (the loop's step is then a quarter sample, so the first frame out is as
clean as the rest), and stops when the receiver unlocks or the train is pinned anew: what
leaves is never a frame with a jump in it.

## amp_out, dsp_core, spdif_tx

`amp_out` is MOST25-to-AUDIO's with its two clock domains folded into one: the commands and the
frame bytes came in clk_s, the engine and the outputs ran in clk_r, the Si514's 1024 Fs. Here
everything is one clock, the engine starts on the tick of phase 0, the coefficient banks switch
between two runs as before and take a set only whole (by its tag), and `spdif_tx` draws
its half-cells from the ticks: one opens on every eighth. No injection, no I2S. `spdif_tx`
puts the line out as 8 samples a clock (`word`, for OSER8 as `fs_fine` does it): the tick
names the sample its half-cell opens on, and the edge lands there. The coding is unchanged
(IEC 60958-3 consumer, 24 bit, the rate in the channel status).

## The board top and its pins

`board/top_tangnano20k.v` wraps `reader_core` for the reader board (`reader_hw`). The board wires
three FPGA pins and nothing else:

| FPGA pin | Header pin | Net | Use |
|---|---|---|---|
| 27 (LCD_B7, IOB8[A]) | 8 | RX_IN, from U3 | the ring's line, IDES8 at 792 Msps |
| 42 (LCD_R3, IOB42[B]) | 25 | SPDIF_F, to R28 and J6 | the S/PDIF line, OSER8 on the same grid |
| 16 (LED1, bank 6) | 7 | 3V3_SW, to U3 and J6 | held high, the strongest drive: U3's and J6's supply |
| 69 (PIN69_SYS_TX, bank 1) | none | the module's USB-UART bridge (BL616), its RX | the ring log, 3 Mbaud 8N1 |
| 70 (PIN70_SYS_RX, bank 1) | none | the bridge's TX, pulled up | the laptop's commands to the log |

The two signals are shared on the module only with its empty LCD connector. Pin 28, the other
half of pin 27's IOB pair, is left unwired; pin 42's other half has no pin on the QN88 package.
Pin 16 is a supply: J6 (PLT237/T10WH) takes 5.5 mA typical, 10 at most, U3 microamps; the module's own 3.3 V
pins sit at its bottom, and their line up to U3 and J6 would have to cross /WAKE with a jumper on
the board. Bank 6 carries only the LEDs besides it, away from the crystal's bank 7 and the serdes
pins' banks 5 and 4. The rest is the module's own: the 27 MHz crystal on pin 4, five LEDs on
pins 15, 17..20 (their header pins are not wired) and the audio amplifier's enable on pin 51,
held low. 5 V comes in on header pin 21 through D3, ground on 20, 22 and 35; the module's
3.3 V pins are not used. `tools/check_pins.py` reads the sheet's netlist and the `.cst`
and fails if they part.

The clocks are the listener's: 27 MHz x 44 / 3 = 396 MHz from the rPLL feeds both serdes as
FCLK, and CLKDIV /4 makes clk_s, 99 MHz. `sim/run_oser.py` runs Gowin's own OSER8, IDES8 and
CLKDIV models: the OSER8 sends D0 first and D7 last, and a random stream sent through OSER8
into IDES8 comes back bit for bit in order, so bit 0 is the earliest sample on both sides, as
`reader_core` assumes.

LEDs, active low: 0 receiver locked, 2 frame train running, 3 frame parity known, 4 one of our
messages decoded (85 ms flash), 5 a block dropped (flash) or an engine overrun (stays on).
LED 1 is dark: its pin is 3V3_SW.

Two resets: rst_p, power-up only, for the log and rx_runlen; rst_s for the core, power-up or the
log's hold (the supply's loss emulated while the laptop is attached, LOGGING.md), in one
registered net.

Build: `cd board && python build.py` writes `build_id.vh` (the commit, bit 31 set for uncommitted
changes; the log sends it in every STATUS), runs `gw_sh build.tcl` and then `check_timing.py`,
which fails when a clock misses its constraint or keeps less than 10 % margin. Place and route
run in Gowin's timing modes (`place_option 1`, `route_option 1`). gw_sh now and then exits at
once with nothing written; build.py runs it again then (twice at most).

`python sweep_ids.py` builds the same gateware eight times with other build IDs. The ID is a
constant in the STATUS record and moves the placement: one gateware kept 1.9 % with one ID and
12 % with another. The sweep shows that spread and fails only on a build that misses the clock;
the 10 % is required of the bitstream that ships (build.py, make_kit.py --fpga).

Cold start: the FPGA configures itself from the module's SPI flash every time the ring wakes it
(5V_SW comes with WAKE). Gowin reads the flash one bit a clock at 2.5 MHz by default: the
7.26 Mbit bitstream would take 2.9 s, long enough to miss the head unit's Connect after every wake.
`build.tcl` sets the loading rate to 25 MHz (`-loading_rate 250/10`): 290 ms (Gowin UG290,
Table 3-3; the limit is 66.6 MHz, 25 is well inside it). Compression would halve it again (58 %
of the bitstream is zero bytes), but this gw_sh accepts `-bit_compress` and still writes an
uncompressed bitstream (its header says `Compress: OFF`), so it is not set. The bench's COLD
measurement (LOGGING.md) gives the real figure, the buck's start and the flash included.

### Timing on the chip

The paths that miss 99 MHz in one clock, all of them in the reader's own logic, which the
simulations cannot see, are taken apart into registered steps, the module doing exactly what
it did:

| Where | What missed | What it does now |
|---|---|---|
| `ctrl_decode` | a block's match, format check and table writes in one clock (16 ns) | three steps (decode and compares, the message, what it does to each stream); the tables written together in the last; commands leave 3 clocks later, positions and levels still take effect on the same frame |
| `dsp_core` | OUT's rounding: Gowin built acc + 2^32 as a ripple of LUTs (16 deep) before the saturation | the rounding spread over the three clocks acc holds still (proved equal for all 2^72 values); the D-write decoded a clock early; out_w lands 2 clocks later, 1600 clocks before spdif_tx reads it |
| `amp_out` | the commit's tag compare into the bank switch | the compare registered with the word (proved equal clock for clock) |
| `nco_frame` | the period (history read, subtract, range check) and the frame edge's error (subtract, wrap, correction into the 56-bit train) in the edge's clock; the train's own compare of the next tick against the word counter | the edge's result lands 3 clocks later (the correction is relative, so the train ends up where it did); the period and the error's subtract start a clock early from `rx_framer`'s `fe_next` (the edge's time, a clock before `fe_valid` brings it); the train keeps the time to its next tick as a register, so "a tick is due" is a sign bit; the adders' operands are set up a clock ahead |
| `rx_framer` | one path just under the margin | a compare of two registers |

Four more paths near 9 ns, which placement alone pushes over or under the 10 % rule, are taken
apart (the S/PDIF coder works out the next half-cell a clock ahead; the edge's take of the
period is the last choice of each register it sets; the history's RAM output goes through a
flip-flop before the subtract; the history range register is copied by synthesis), each exactly
equal in what it does. Setup and hold met everywhere; the one warning left is PR1014 (the
crystal reaches the PLL on general routing), as on the listener.

Eight IDs (`board/sweep_ids.py`) found the paths that placement can make slow, each cut so that
what goes out stays the same but for the byte activity's interval, a clock earlier at both ends:
- the byte activity's compare a clock before the mask bit;
- the position trigger's zero test kept beside its counter (pos_z);
- the peaks compared against all eight at once;
- STATUS's lane pick on a copy of the writer's index of its own (wi1);
- the writer's index set to 0 at the gap's end, not by its pick;
- the BLOCK record's "the next block began" and "the line stopped" compares (bi_t <= last_bi,
  fmask != 0) a clock ahead: both hold still for hundreds of clocks round a byte 0 and for
  STOP_US before the line is called stopped; ba == 0 taken with ba_t, its own tap;
- ctrl_decode's channel + 1 for a position added at E2 (pdp), the SinkInfo/Connect pick alone
  left at E3 (pd holds from E1 to the next telegram);
- rx_framer's input stages kept apart from rx_classify's registers, which they equal bit for bit
  and which synthesis would merge them into (the framer's decode then fed from the classifier's
  corner).
The byte activity also has a seen mask (a byte counts from its second write after power-up): on
the chip prevb starts at 0, in a simulation X, and without it the first STATUS after power-up
would mark standing bytes the simulation cannot show. Over eight IDs the margin still spreads
(0.7 to 20.9 % in the last full sweep): the chip is 82 % full and placement decides which path
comes last. So the 10 % is checked on the build that ships, and the sweep only shows the spread.
ctrl_decode's command-01 pick (pos_pend -> ps -> pos_b -> p, the worst path) has a clock of its
own (p01_q, a clock ahead of the command; checked by run_ctrl.py and run_e2e.py).
The chip is 57 % logic, 59 % registers, 86 % of the slices, 28 of 46 BSRAM (16 of them the
capture), 4 of 24 DSP; a build gave 117.0 MHz, 18.2 %. The figure that counts is the build that
ships, in `kit/2_fpga/BUILD.txt`.
The checks that it still does the same: `run_ctrl.py`, `run_nco.py` (with three corners added
that put the train's tick at UI 0 next to the edge's clock), `run_amp.py`, `run_e2e.py`; the
tick logs of every `run_nco.py` corner equal, line for line, those of the reviewed intermediate
version; the reworked `nco_frame` and `ctrl_decode` were each checked against their earlier
forms by independent cycle models (0 differences over millions of clocks).

## Verified, and how

```text
python reader_gw/sim/run_ctrl.py          needs oss-cad-suite on PATH
python reader_gw/sim/run_nco.py
python reader_gw/sim/run_amp.py
```

`run_ctrl.py`: `tb_ctrl.v` plays frames into the decoder as the framer delivers them, parity
included, and logs every command; `ctrl_model.py` is given the same frames and must produce the
same commands, one for one and in order, in five scenarios: the JLR messages in a plausible
sequence (connect, levels by both messages and their precedence, mute all and one, SinkInfo
formats, Result and Error, silence by dB, +18 dB); everything to refuse or ignore (segments,
5 or 3 channels, channel 60, an unordered list, sinks 0 and 5, Get, another FBlock, short
payloads, a system message, blocks with the index unknown or the receiver unlocked, idle blocks,
MOST High Protocol, bad addresses, a Result or Error with nothing on, a DisConnect from another
device); the Ack forms with a SenderHandle, Status replies from the amplifier, on a ring of odd
parity; the parity check (a data bit, a control byte and the parity bit itself flipped, a stretch
of random parity that makes the check forget itself, learning anew); and 400 random blocks, 60 %
of them well-formed messages with random values, the rest off in one way, with a flipped bit in
one frame of 40. It also checks that `rtl/gain_rom.vh` is what `gain_tables.py` writes today.

`run_nco.py`: frame edges made in Python, all at 48 kHz, the rate of JLR: exact, +1000 ppm with
2 samples of jitter, -1000 ppm with 3 samples, a 40-frame lock gap, a jump of the frame timing
by 3000 samples, steps of 150, 160 and 170 samples earlier (the train's tick at UI 0 then falls
next to the edge's clock); delivered 160 samples late as the receiver does, each announced on
fe_next a clock before. Every running frame has
exactly 1024 ticks; the ring's UI 0 falls 128 ticks before the train's frame start to within
the edges' own jitter and the offset does not wander; every tick interval is the period to
within the grid and the loop's step; the period comes out to 1 ppm (4 ppm with jittered edges,
as two jittered edges 64 frames apart give); the train stops in the gap and runs again after
it; at the jump it is pinned anew and runs again within a few frames.

`run_amp.py`: `tb_amp.v` is MOST25-to-AUDIO's `tb_dsp.v` on the train at 48 kHz: four sources
in the frame, four coefficient sets written with tags, a word lost, a commit lost, a stray word,
refused commands; PICK, BANK, TXN, MODEL, TIME as there (every run on the right bytes, banks
never written in use, the switches exactly for the whole sets, every output equal to the
bit-exact model), and SPDIF in place of I2S: the line read back off the 1.26 ns grid
(`spdif_line.py`), every frame well formed (`spdif_dec.py`: preambles, cells, parity, the
channel status with the rate), one S/PDIF frame per ring frame, the samples the runs' outputs
frame for frame (3991 of 4049, the first ones before the first set), and every run of the line
a whole number of half-cells to within 0.91 samples: the edges sit on the grid.

`run_e2e.py`: the whole reader from the line. `ring_stim.py` makes a JLR ring as the sampler
sees it: the head unit's stereo at channels 8..11, a second stereo at 30..33 it switches to
later, mono sources at 20, 21 (sink 2, navigation), 24, 25 (sink 3, the parking sensors) and
26, 27 (sink 4, the chimes), the other channels random, and in the control channel the head
unit's telegrams - Connect and its Result for each, SpeakerLevel to sinks 1 and 4, the
gateway's levels with byte 8 and byte 10, Mute on and off, DisConnect and the second Connect -
Biphase Mark coded,
distorted inside SP4 (pwd +0.15 and -0.15 UI with 0.195 UI of jitter, +500 and -500 ppm, both
preamble sets) and sampled as the IDES8 does. `tb_core.v` drives `reader_core` with it and
logs every link, and the checks are: RX, every frame the receiver completes equals the frame
sent; CTRL, the commands the decoder sent equal `ctrl_model.py`'s for the frames the receiver
delivered; PICK, every engine run starts on the bytes at the positions the commands set; MODEL,
every output equals the bit-exact model's; SPDIF, the line read back is well formed, one frame
per ring frame, the samples the runs' outputs frame for frame, the edges within 1.5 samples of
a whole half-cell (the grid plus the loop's share of the line's own jitter); GAIN, at the end
of the 2000-frame run the output is the second stereo times the SpeakerLevel's -20 dB plus the
navigation source times its 0x409 byte 8 level, the parking sensors times their byte 10 level and
the chimes times the SpeakerLevel to sink 4 (-14 dB), to 0.2 %. At pwd +0.316 UI with the full jitter the
low pulses fall to 0.59 UI, outside SP4's 0.743 UI validity bound; there the receiver lost one
frame in 2000 and its lock with it, and the reader's output restarted cleanly 8 frames later.

Two checks against code written earlier and separately, the MOST25-to-AUDIO host in C:

```text
python tools/crosscheck_most_msg.py      the block parser against most_msg.c
python tools/crosscheck_gains.py         the gain words against sound.c + dsp_img.c
```

### The ring log, from the line to the laptop's parser

`sim/run_log.py` runs the whole reader with the log, its times shrunk (a "millisecond" of 20 us, a
capture of 256 entries), the laptop's commands on uart_rx, and checks the log's UART line bit by
bit, then every record against `sim/log_model.py`, built from what the testbench saw inside the
core: every BLOCK byte for byte (partial blocks too), every position command and coefficient set,
the STATUS counters and state at the clock each was taken, every lock, index, train, parity,
commit and bank event with its argument and time, every dump as a contiguous stretch of the
line's runs or frame bytes with the trigger at its place; then `tools/log_decode.py` on the same
bytes, whose replay of the raw blocks through `ctrl_model.py` must give exactly the decisions the
FPGA logged. Corners: a ring with the head unit's telegrams, a mark, a frames capture, the laptop
attached and a soak-test burst; the ring dark for 1.5 ms with the laptop attached (the core held,
everything learnt anew after the wake); two frames lost after the lock held (the unlock capture);
the module powered with the ring asleep (the core held from DARK, the first edge starts COLD,
nothing decoded before it ends). `tools/test_log_format.py` runs the parser over damaged streams.

## Not proved - what only a recording of the car settles

- Which volume message the XF's amplifier gets: 0x46D in dB (usb2most saw it on Freelander 2
  and the AUD3 amplifiers) or the gateway's 0x409 (JLR-HU saw it on the XF). Both are decoded.
- The 0x409 byte positions (2, 8, 10: from one parser) and its raw-to-dB curve. The table in
  `gain_rom.vh` is the host's placeholder, (raw / 40)^2, full from 40 up.
- Whether the stock head unit sends 0x22.0x111 Connect at all, and whether it asks the
  amplifier for SinkInfo; the fallback for a missed Connect is the source's Allocate.Result,
  not coded until a recording asks for it. Cold start: a Connect sent while the FPGA still
  configures leaves no position until the next source change or SinkInfo; the FPGA's
  configuration time against the ring's wake order is for a capture.
- Whether the ring's frame parity is one value on every frame (the check learns it, and
  switches itself off where it is not).
- Whether the gateway repeats 0x409 or sends it on a change only. Until a level is heard the
  streams play their start-up levels.
- Whether JLR mutes with 0x113 Mute, decoded here, or with 0x466 MuteParameters, which
  usb2most's firmware uses and which is not decoded.
- 0x22.0x467 MixerLevel, among the XF amplifier's messages in Rhys Morgan's projects, is not
  decoded; MOST25-to-AUDIO's host puts it on top of each stream's level. If the car sets the
  prompts' or the chimes' level with it, the reader does not follow.
- Whether anything sends a Connect, DisConnect or Mute to the gateway's shadow amplifier, 0x22
  instance 0xA1 at node 0x161: the InstID is not checked, so the reader would take it as the
